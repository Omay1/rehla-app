# رحلة REHLA — بداية المشروع

واجهة عربية RTL متجاوبة للموبايل والكمبيوتر، قابلة للتثبيت كتطبيق ويب تقدمي (PWA)، وفيها نموذج أولي لتصفح المحلات والمنتجات والسلة والطلب النقدي ولوحة إدارة تجريبية.

## مهم قبل الاستخدام التجاري

هذه الحزمة **نسخة أولية تجريبية وليست نظام توصيل منشورًا أو جاهزًا لاستقبال طلبات حقيقية**. البيانات الحالية تُحفظ في `localStorage` على الجهاز والمتصفح نفسه؛ لن تظهر تلقائيًا على أجهزة العملاء أو المحلات أو المناديب. تسجيل الدخول التجريبي ليس حماية إنتاجية. لا تنشر النسخة بهذه الحالة لاستقبال بيانات عملاء حقيقية.

## فتح النسخة

- افتح `index.html` في المتصفح لمعاينة الواجهة. بعض مزايا PWA تتطلب استضافة HTTPS.
- كلمة مرور لوحة الإدارة التجريبية: `Rehla@2026` — غيّرها ولا تعتمد عليها للحماية الحقيقية.
- المحلات والمنتجات الموجودة بيانات تجريبية للتوضيح، وليست محلات فعلية.

## الملفات

- `index.html`, `style.css`, `app.js`: الواجهة والمنطق التجريبي.
- `manifest.json`, `sw.js`, `icon.svg`: إعدادات PWA.
- `config.js`: مكان إعداد عنوان Supabase والمفتاح العام.
- `database.sql`: مخطط أولي لقاعدة البيانات.

## حالة النسخة الحالية

تمت إضافة تكامل لوحة الإدارة مع الجداول المشتركة عند ضبط Supabase، وإدارة مراجعة طلبات المحلات، وتعيين المندوب، وإنشاء حساب مندوب بدعوة بريد إلكتروني. كما أضيفت migration ثالثة وGitHub Actions لنشر migrations ووظائف Edge. شغّل `python tests/smoke_test.py` للتحقق المحلي. هذه الاختبارات لا تتصل بخدمات حية ولا تثبت أن النشر تم.

## ما يلزم لإطلاق حقيقي

1. إنشاء مشروع Supabase، وتشغيل `database.sql` بعد مراجعة سياسات الأمان.
2. إكمال ربط التطبيق بالـAuth والجداول ورفع صور المنتجات إلى Storage.
3. إنشاء صلاحيات آمنة للأدوار: مدير، صاحب محل، عميل، مندوب. يجب تنفيذ إنشاء الطلب وحساب الأسعار على الخادم، لا الوثوق بإجمالي يرسله المتصفح.
4. إنشاء تطبيق مندوب فعلي أو واجهة مندوب متجاوبة، وربط توزيع الطلبات والإشعارات.
5. اختبار سياسات RLS والطلبات على أكثر من حساب وجهاز قبل النشر.
6. نشر الواجهة على استضافة HTTPS، ونشر الـBackend/Functions وإعداد الدومين إن لزم.
7. تطبيق `supabase/migrations/20261015000400_release_hardening.sql` بعد migrations 20261015000200 و20261015000300؛ والأفضل إدارة التغييرات من خلال `supabase/migrations` وترحيلها بالترتيب.
8. راجع `DEPLOY_FROM_PHONE.md` لخطوات النشر من الموبايل، و`RELEASE_STATUS.md` لحالة الاختبارات والقيود الحالية.

## إعداد Supabase

ضع `SUPABASE_URL` و`SUPABASE_ANON_KEY` في `config.js` فقط بعد تجهيز المشروع. المفتاح المسموح للواجهة هو المفتاح العام (anon/publishable) مع سياسات RLS صحيحة. **ممنوع وضع `service_role` أو أي سرّ في ملفات المتصفح.**

## استضافة مجانية

يمكن تجربة استضافة الواجهة على GitHub Pages أو Cloudflare Pages أو Netlify، لكن هذه الاستضافات للواجهة فقط. تحتاج قاعدة البيانات والـBackend إلى خدمة منفصلة، والخطط المجانية لها حدود وقد تتغير. يجب ربط الخدمات واختبارها قبل اعتبار التطبيق منشورًا.


## حزمة الخادم الخلفي المضافة

أُضيفت دالة Supabase Edge Function في `supabase/functions/create-order/index.ts` لإنشاء الطلبات بعد التحقق من جلسة المستخدم وإعادة حساب الأسعار من قاعدة البيانات، بالإضافة إلى مسودة سياسات RLS في `supabase/migrations/20261015000200_security_and_policies.sql`. راجع `BACKEND_NEXT_STEPS.md` لمعرفة خطوات الإعداد. **هذه الملفات لا تعني أن الواجهة متصلة بها تلقائيًا**؛ يلزم إكمال ربط تسجيل الدخول والـcheckout ثم نشر الدالة واختبار الصلاحيات قبل استقبال طلبات حقيقية.

## تحديث Backend إضافي
تتضمن الحزمة الآن `supabase/migrations/20261015000300_auth_workflows_and_order_ops.sql` لإنشاء profile عند التسجيل، وتقييد تحديث حالة الطلب حسب الدور، وتعيين المندوب بصلاحية المدير. كما تتضمن Edge Functions لـ`update-order-status` و`assign-courier`. راجع `BACKEND_NEXT_STEPS.md` لترتيب التهيئة. هذه ملفات كود غير منشورة؛ واجهة التطبيق ما زالت تجريبية وتحتاج تكاملًا مع Supabase قبل الاستخدام الفعلي.

## نشر الخادم من GitHub Actions
يوجد workflow باسم `Deploy REHLA backend` داخل `.github/workflows/deploy-supabase.yml`. بعد رفع الملفات للمستودع، أضف `SUPABASE_ACCESS_TOKEN` و`SUPABASE_PROJECT_REF` و`SUPABASE_DB_PASSWORD` في GitHub Actions Secrets. يقوم الـworkflow بربط المشروع، وتطبيق migrations بالترتيب الزمني، ونشر وظائف Edge الأربع. راجع `DEPLOY_FROM_PHONE.md` قبل التشغيل. لا تضع مفاتيح سرية في `config.js` أو في المستودع.
